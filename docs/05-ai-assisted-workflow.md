# AI 辅助测试：控制范围，保留判断与证据

AI 在本实践中用于代码检索、风险提示、测试草案和最小修复建议。业务预期、授权范围、证据真实性及交付判定仍需由使用者审查。作品集中不将辅助生成内容表述为全部手工独立产出。

## 1. 给每次任务一个明确边界

输入包含：目标模块、允许读取/修改的文件、现有失败与环境、需要回答的问题、可执行命令、验收结果。先读取索引与目标文件，使用带路径限制的检索；避免把依赖目录、完整日志与无关资料全部放进上下文。

“候选风险”与“已确认缺陷”分开报告。看到某种代码形态只能形成假设，必须进一步确认业务预期和可复现影响。

## 2. 按阶段组织协作

| 阶段 | AI 的交付 | 审查重点 |
| --- | --- | --- |
| 基线 | 命令、结果、范围与环境限制 | 是否真正执行；有没有跳过、已有失败或未提交改动 |
| 定位 | 候选问题、触发条件、源码证据 | 是否把需求、代码与数据约束混淆 |
| 复现 | 最小用例和修复前失败输出 | 是否因目标缺陷失败；业务预期是否正确 |
| 修复 | 可审查 diff 与影响范围 | 是否越界、降低断言、改阈值或混入重构 |
| 回归 | 缺陷用例、模块子集、必要的全量结果 | 是否对应当前源码快照；失败是否如实保留 |
| 总结 | 已修、遗留、未验证与证据索引 | 是否存在未经验证的效果描述 |

已有任务授权足够时可以连续完成这些步骤，不需要机械地每一步停下来请求确认。业务口径不清、涉及跨模块设计或会扩大影响时，再提交具体方案供判断。

## 3. 四个固定定位问题

1. 模块公开入口、权限和依赖边界是什么？
2. 失败如何表示，HTTP 与业务码是否符合当前项目契约？
3. 金额、数量、比率与时间计算是否在边界上保持正确口径？
4. 未覆盖分支有什么业务含义，是不可达逻辑还是遗漏场景？

问题应服务于本轮风险。例如没有金额运算的模块，不必强行寻找舍入问题。

## 4. 对 AI 输出做反证检查

- 用例通过前，确认它在修复前确实能失败；必要时临时恢复对应旧实现再验证，保护其他改动。
- 检查断言是否仍检查金额、状态、记录数量等核心条件，避免仅检查响应“存在”。
- 对两算法或两统计路径的一致性，再增加人工小样本作为独立参照。
- 对“已验证”逐项核对运行记录；工具调用失败、超时或未启动不算通过。
- 对覆盖率、提效与缺陷数量要求明确分母与来源，无法证明的数字不写。
