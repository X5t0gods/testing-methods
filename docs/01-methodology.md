# 测试方法：从业务风险到验证闭环

本方法来自社区超市管理系统的测试与修复实践。系统涉及商品、库存、采购、收银、会员、促销、报表和智能分析，测试重点是资金与业务数据的正确性。

## 1. 明确测试目标与判定依据

每轮先写清“对象、触发条件、预期行为、观察点、结束条件”。例如，验证结算失败时，不能只检查返回了错误提示，还要观察库存、流水、付款记录是否产生残留。

| 信息 | 要回答的问题 |
| --- | --- |
| 业务目标 | 本轮保护什么：金额、库存、权限、流程还是展示？ |
| 业务依据 | 预期来自已确认的需求、数据约束还是接口契约？有无冲突？ |
| 输入条件 | 哪个角色、哪些数据、哪个时间窗口、是否重复或并发调用？ |
| 可观察结果 | HTTP 状态、业务码、返回字段、持久化状态和关联记录分别应如何变化？ |
| 通过标准 | 什么输出足以判定通过？什么情况只能标为未验证？ |

需求表达预期行为，代码提供实际行为，数据库约束提供一致性边界。三者冲突时保留差异并确认口径，不能单凭“代码现在这样做”判断它正确。

## 2. 建立可比较的基线

记录测试日期、源码提交及未提交改动、Python/Node/数据库版本、依赖锁定方式、测试数据规模、运行命令、退出码和测试结果。

全量测试、无数据库测试、模块子集、接口冒烟的用例范围不同，应分别计数。数据库不可用导致的 skip 表示未执行，不能合并到 passed。覆盖率还必须标注采集范围、是否包含分支和是否包含集成测试。

基线阶段以检查为主，但 pytest、覆盖率采集和浏览器脚本可能产生缓存、日志或测试库写入。因此，“不修改业务代码”与“没有任何写操作”需要分开表达。先检查夹具与连接目标，再决定是否运行。

## 3. 按风险确定优先级

| 优先级 | 典型风险 | 优先验证点 |
| --- | --- | --- |
| 高 | 资金错误、库存错误、未授权访问、事务不一致 | 舍入、重复结算、并发扣减、退货限额、权限边界、失败回滚 |
| 中 | 业务流程断链、统计口径错误、接口契约漂移 | 状态迁移、空值、时间窗口、门店隔离、字段与类型 |
| 常规 | 文案、交互和一般输入体验 | 校验提示、加载状态、空态、分页和导出反馈 |

优先级是排期依据，不代替实际严重度判断。高覆盖率模块也可能包含业务缺陷；低覆盖率只是寻找漏测分支的线索。

## 4. 组合测试设计技术

| 技术 | 项目中的用法 | 示例观察点 |
| --- | --- | --- |
| 等价类 | 合法/非法输入、存在/不存在的对象、不同权限角色 | 返回状态、错误码与数据是否一致 |
| 边界值 | 金额半分、数量为零、恰好安全库存、截止时间、算法阈值 | 等于边界与刚跨过边界的行为 |
| 状态迁移 | 草稿、提交、收货、作废、退款等状态 | 合法迁移成功；非法迁移无数据副作用 |
| 决策表 | 多类促销、会员折扣、优惠券与支付组合 | 组合条件是否互斥、叠加或优先 |
| 幂等与并发 | 同一业务请求重复提交；多个客户端同时执行 | 业务效果一次、编号不重、库存不超扣 |
| 不变量 | 库存与流水勾稽、金额组成、退货不超过可退量 | 操作前后约束持续成立 |
| 差分验证 | 实时统计与预聚合；两种关联算法 | 同数据同参数下的结果一致性 |
| 故障注入 | 在事务中间阶段抛错、模拟依赖失败 | 无半成品、可重试、状态可解释 |

不变量是业务模型的一部分。例如库存可写成“期初数量 + 期间入库 − 期间出库 = 期末数量”；若流水已包含期初，则比较当前库存与全部有符号流水之和。必须先明确时间范围与期初口径，不能把两个公式混用。

## 5. 分层安排测试

| 层级 | 主要目的 | 不能替代的验证 |
| --- | --- | --- |
| 静态检查 | 类型、未定义变量、明显代码问题与契约缺口 | 不能证明业务流程正确 |
| 纯逻辑单测 | 金额、格式、分类归属、促销条件与算法边界 | 不能证明数据库事务与真实权限 |
| 服务与数据库集成 | 状态、事务、唯一约束、并发与回滚 | 不能证明浏览器交互正确 |
| 接口测试 | HTTP 状态 + 业务码 + 响应结构 + 权限 | 不能只检查业务码而忽略 HTTP 状态 |
| 浏览器运行时与流程 | 真实请求、控制台错误、关键页面路径 | 页面能打开不等于流程可用；Mock 通过不等于真实接口通过 |
| 性能与容量观察 | 延迟分位数、失败率、样本数与条件 | 单次耗时或平均值不能替代 P95/P99 |

## 6. 单缺陷闭环

1. 用受限文件清单定位候选问题，记录源码位置和触发条件。
2. 明确业务预期与最小反例，先排除无数据、错误账号、配置或环境问题。
3. 编写能识别该缺陷的用例，并记录修复前失败的原因。
4. 进行范围可审查的最小修复，不混入格式化、依赖升级或无关重构。
5. 验证原反例通过，并增加必要的相邻边界，避免仅对一个输入写特判。
6. 运行模块子集，再按影响范围安排集成或全量回归。
7. 审查 diff、断言强度、数据残留和报告，保留提交检查点。

原始流程中的“每个修复不超过 15 行”用于控制探索范围。本作品集将其保留为经验提醒，不视为通用质量标准：需要较大修复时，应说明影响和验证方案。若测试预期本身错误，先说明业务依据，再审查修正；不能默默放松断言。

## 7. 收尾与交付

交付物包括：基线记录、缺陷清单、最小复现、修复摘要、回归用例、实际输出、前后对照与未验证项。若引入新失败，定位到具体变更，保留现场，再撤销对应变更；不使用丢弃整个工作区的命令处理混合改动。

多个工作同时修改项目时，记录测试对应的源码快照，避免把不同时间的通过数拼成一次结果。方法文档的版本也不等于业务项目的发布版本。
