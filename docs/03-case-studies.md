# 案例复盘：让缺陷与验证方式一一对应

以下案例根据项目测试实践整理，省略业务标识、连接信息和原始数据。两份独立示例是重新编写的教学代码。

## 案例一：金额半分边界

**风险**：收银试算与结算若使用不同舍入口径，同一笔交易可能相差一分。普通整数或两位小数测试难以触发该问题。

**设计**：采用精确十进制输入，例如 `0.125`，先根据已确认的财务规则确定两位小数采用 `ROUND_HALF_UP`，预期为 `0.13`。同时覆盖零值、相邻值、大金额与负数边界；负数规则也必须明确。

**定位与修复**：检查各计算阶段的数值类型、量化时机与汇总顺序。避免把二进制 float 与内置 round 作为上述十进制规则的替代。修复必须对齐完整金额链路，不能只改最终展示。

**验证**：同一组用例先运行存在舍入问题的示例实现，再运行修复实现。参见 [金额回归示例](../examples/money_regression.py)。该示例证明用例能够识别边界问题，不单独证明原系统所有金额路径均正确。

## 案例二：多门店同日数据被覆盖

**风险**：聚合结果包含多条相同日期、不同门店的记录，若按日期直接赋值，后读到的门店可能覆盖之前的金额。

**设计**：构造同一天两个门店、另一日期一个门店的数据，明确跨门店汇总与单门店过滤分别应满足的结果。再覆盖记录顺序打乱、空结果、同名门店与金额小数。

**定位与修复**：追踪查询过滤、分组键与结果组装，区分“同一业务对象的新版本覆盖”与“多个对象的指标累加”。业务标识使用稳定 ID，避免以名称作为唯一键。

**验证**：在最小样本上人工验算，再用不变性检查确保输入顺序变化不影响总额。参见 [汇总回归示例](../examples/report_aggregation.py)。对应项目专项的覆盖率结果见[效果页](02-results.md)。

## 案例三：部分预聚合记录导致统计缺失

**风险**：某个时间窗口仅有部分日期或门店完成预聚合，若仅检查“存在聚合记录”，返回的看板结果可能缺少未聚合部分。

**设计**：分别构造无预聚合、完整预聚合、缺一天、缺一个门店和作废交易后的数据。以相同口径的实时计算结果作为对照，核对时间、门店、有效状态与退货扣减。

**定位与修复**：检查预聚合覆盖范围是否完整，并确认回退策略是否会重复计算或漏算。重算时还要处理已无有效交易但仍残留的统计键。

**验证**：同时比较总额、分日结果与门店结果；执行重算两次验证幂等；操作前后检查库存和交易数据未被统计任务意外改变。

## 案例四：算法阈值与存储舍入

**风险**：支持度等阈值比较受浮点误差影响；若先舍入支持度再计算置信度或提升度，可能漏规则或错误纳入临界规则。

**设计**：从能手算的小事务集开始，固定事务快照与全部参数。覆盖“恰好达到阈值”“略高于阈值”“真实提升度等于 1”“空数据”等情况，再比较两算法的项集和规则。

**定位与修复**：区分计数、计算精度、筛选精度与展示精度。阈值筛选遵循原始业务参数，存储或展示量化放在适当阶段；不能靠降低阈值消除差异。

**验证**：除比较两算法相互一致，还需与手工预期或独立计数结果比较。两个实现一致也可能共享同一错误。性能实验必须另外记录数据规模、参数、计时边界与采样限制。

## 这些案例体现的测试判断

测试并非只列输入和预期，还要解释“为什么该输入能打到风险、怎样区分环境问题与业务缺陷、哪些观察点能够证明副作用正确”。缺陷修复以失败复现和回归证据为基础，覆盖率用来发现遗漏与说明执行范围。
